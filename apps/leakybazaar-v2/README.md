# LeakyBazaar control v2

Private workspace `leakybazaar-v2@0.1.0` is a separately versioned control candidate copied from historical LeakyBazaar at `945f1a86`. It fixes the reproduced F1/F2/F3 races and the additional concrete control defects below. Historical LeakyBazaar, frozen campaigns, patches, baselines, packs and contracts stay unchanged. A new control campaign and independent audit remain required before calling it an accepted correct control.

Razorpay INR refund inputs below its pinned ₹1.00 minimum are rejected locally before creating a reservation or sending any refund POST (contract `refund.minimum-amount`). This prevents a lost response to a request that could never be accepted from creating an unrecoverable ambiguous reservation. It does not retrospectively release old unknown reservations or assume minimum limits for other currencies.

API refund requests first commit a reservation in `refund_requests`, including the payment reference, exact amount, line and original idempotency key. Before its first refund POST, the app also saves the provider target used in the URL and durably marks that the POST may have started. Reservations reserve both line and order capacity but are not exposed as observed provider refunds. The app attempts the provider call after commit and scans due reservations after startup, sending only requests whose durable state shows no prior POST under a process-independent advisory lock. Once a POST may have started, an unknown outcome or a crash retains capacity with bounded backoff and awaits exact provider reconciliation; it is never resent without proof of a valid retention window. Only a first POST's exact provider response identifying an insufficient refundable amount or Razorpay's cited minimum-amount validation failure can close the request as `rejected` and release its reservation; an earlier ambiguous attempt prevents another POST or release of the reservation. A rejection has a persisted reason, distinct from `linked` success. Provider responses and signed webhooks use echoed `refund_id` metadata/notes to correlate the request; contradictory returned identities are rejected. A shared transaction serialises mutations under the order lock. Each refund recognises money once and reverses it at most once. An uncorrelated event retries when its immutable amount could belong to an unresolved API request. A different amount excludes that identity, allowing unrelated provider effects to be recorded independently. Equal amounts never establish identity; exact request metadata or the exact API response is required. Importing an unrelated effect never resolves an uncertain request.

Razorpay order responses can omit `receipt`; the adapter then uses `notes.order_id` if supplied. If both identities appear and disagree, checkout fails. Razorpay refunds use the documented `X-Refund-Idempotency` header through the pinned SDK's HTTP client; a refund `receipt` alone does not replay an unknown result. The SDK seam remains redirected to the simulator in MoneyInvariant runs.

Stripe refunds use a dedicated instance of the pinned SDK with its public Fetch HTTP client and zero automatic network retries. The pinned Node HTTP client retries a closed connection once even when `maxNetworkRetries` is zero, which could hide a first uncertain refund POST behind a later rejection. Checkout also uses Fetch/zero retries; capture retains the standard SDK client's retry behavior; the durable refund worker sends only requests with no possible prior POST.

Concurrent checkout calls compete for one atomic durable create marker without holding a pool connection across provider I/O. In-flight contenders receive an explicit unknown-outcome response; later calls reuse the recovered provider reference. This prevents a second untracked Razorpay order during a double submit. Before any payment-create I/O, checkout commits a durable attempt marker. A retry with no recovered provider reference returns an explicit unknown-outcome error instead of creating another payment after an idempotency key could have expired. Signed, correlated success callbacks recover the original reference and book once; created/authorised observations recover identity without booking captured money. Order, amount, currency and existing-reference guards still apply. An attempt whose outcome remains unknown is conservatively blocked: availability recovery after an unobserved or definitively rejected create requires separate evidence; the app does not guess that no payment exists.

Transport dedupe uses Stripe Event IDs and the Razorpay event-ID header, with a payload hash fallback when that header is absent. The dedupe marker commits atomically with financial effects. Object/order locks independently prevent repeat financial postings, including deliveries with different event IDs. Distinct lifecycle changes using one `refund.updated` type can therefore both apply. Unknown/unpaid payment references roll back the marker and return 503 for retry.

Captured payments must match the stored payment reference, order identity when supplied, amount and currency. Refunds must match currency and stored identity/amount, and live refunds cannot exceed captured order capacity. Failed/canceled refunds reverse their financial effects; both API and dashboard changes derive the order label from refunds still holding money (`paid` at zero, `partially_refunded` below total, `refunded` at total). Pending provider refunds retain v1's reservation/recognition semantics.

Money stays `bigint` internally. JSON numeric inputs and provider SDK numbers must be nonnegative safe integers; string inputs parse exactly within this control's SDK integer range. Values beyond `Number.MAX_SAFE_INTEGER`, fractional values and rounded/ambiguous inputs are rejected before creating money rows or calling the provider. Decimal-string length is bounded before constructing a bigint.

Use a fresh disposable v2 database. This is a new control schema, not a migration of historical benchmark databases. Both YAML profiles and the typed profile declare financial quiescence only when every durable refund request is resolved. Pending checkout attempts may await a future customer/provider event; they do not claim captured money or permit another create. A persisted reservation whose send marker was never set can issue its first POST after startup. A lost-response or post-marker-crash reservation requires an exact correlated provider observation to resolve; startup never assumes its key is still retained. A first definitive insufficient-capacity or minimum-amount rejection resolves as rejected, allowing a pending uncorrelated dashboard refund webhook to be retried and applied. A provider that continues to refuse ambiguously or never answers leaves the run unsettled rather than producing a clean settled verdict. The provider's key-retention period is not documented in the pinned Razorpay contract, so recovery after that period requires further evidence.

Run `pnpm exec vitest run bench/leakybazaar-v2/test`. Pool barriers and provider callbacks establish explicit schedules without random sleeps. V1 assertions document its reproduced bad outcomes; v2 assertions require correct posting, attribution and acknowledgement. The suite also checks lifecycle permutations, unsafe inputs, provider identity/currency/capacity, labels, concurrent checkout, durable-request quiescence and recovery from a persisted reservation, signed decoding for both providers and exact SDK money round-trips. This is regression/development evidence, not a blind comparator or campaign.

Copied pack selections remain historical examples, not an accepted release-pack choice. No default harness wiring, benchmark score or release criterion changes. Supported-scope precision, complete identity/contract fidelity and independent audits are still evidence obligations; these targeted fixes are not a proof of control correctness.

The optional intermediate work probe delegates to boundary silence (`SELECT true`) because this app has no separate durable worker queue. It does not declare financial settlement: the final probe still requires all refund reservations resolved.

Stripe rate-limit429 responses are pre-execution rejections under the pinned `idempotency.rate-limit-precedes` contract ([official explanation](https://docs.stripe.com/error-low-level#content-errors)). A first such response can reject its reservation; a later429 never releases an earlier unknown attempt. Refund-only SDK calls use Fetch with zero hidden retries so the durable recovery worker sees each uncertainty and does not resend possibly committed calls. Checkout also disables hidden mutating retries; capture and read operations retain their existing retry settings.

V5 postmortem: an ambiguous500 followed by insufficient-capacity400 can remain unresolved even after a full dashboard refund has been correctly recorded. The cited Stripe contract permits later effects after500. Neither current exhausted capacity nor absence from one provider listing proves permanent non-commit; the strict final probe remains false until exact authoritative evidence resolves the request. This is an explicit control recovery limitation, not a clean precision result.

V7 postmortem: a second refund after an expired idempotency key is prevented by refusing another possibly committed POST. This trades automatic recovery of an uncertain call for financial safety. The current provider port has no durable non-commit proof or trustworthy generic retention window; a missing callback can therefore remain UNSETTLED. Simulator key expiry compresses provider retention without advancing app/DB clocks, so development evidence does not establish a faithful 24-hour production timeline.

The exact documented Razorpay 400 concurrency refusal (`api.concurrent-payment-operation-rejected`) closes only a first-attempt refund reservation as rejected. Its status, error code, reason and description must match; a conflict after any possible prior execution cannot erase uncertainty. Generic 400, idempotency conflicts and misleading 500 bodies remain ambiguous.

Pre-blind audit correction: signed refund callbacks trigger a current-object GET under a process-independent per-refund try-lock. Contended callbacks return503 without acknowledgement or a marker. Retrieval runs outside a financial transaction; immutable signed/provider fields must agree, then the same client commits event identity and financial effects atomically. This avoids pool-dependent reentry while serializing reads and writes. Current requires_action can legitimately return to success; delayed old success/pending callbacks observe the current object instead of overwriting it. A late POST reply preserves any already-recorded authoritative status. Unknown GETs are retried, not guessed. Candidate pack0.5.0 and new development validation remain prospective; V9 evidence stays pinned.
